# Coordinator: architecture, use, and verification

Implemented and checked on 2026-10-08. This replaces the earlier proposal in this file. Existing Claude Code work was preserved; nothing was committed or pushed.

## Use it

1. Build/install the macOS app with the repository's normal `make app` / `make install` workflow. `make vscode-install` builds a VSIX with its own matching broker and installs it in VS Code. Existing windows may need **Developer: Reload Window** once. If a bridge shows Disconnected, run **Agent HUD: Reconnect Workspace Bridge**. Keep the app and bundled broker at matching protocol versions.
2. Open **Coordinator** from the panel header or **⌃⌥C**. **Open in VS Code** contains actual connected folders, including projects with no agents. Select a project, then **Assign Work**. Choose Claude or Codex, permissions/sandbox, and a concrete task. Starting a task shows errors in the dialog without throwing away the task text.
   To reply to an existing Codex conversation, select its watched session. The composer shows **This Codex chat**. Send reaches that exact live conversation; a reply during work steers its running turn. If the original chat is closed or reconnecting, its draft stays saved and **Retry Connection** checks the owner again. No Accessibility permission or editor focus is required for Codex replies.
3. Follow the conversation and current activity. **Waiting on you** means a concrete pending request. Permission cards have Allow/Deny; questions support listed options and a typed answer. **⌘.** interrupts. Claude follow-ups queue for the next turn; Codex can steer a running turn.
4. **Completed** is backed by a successful turn-completed event, rather than elapsed time. Read the reply and review **VS Code → Review Changes** in the existing window's Source Control view. Source Control includes all local changes; it is not an isolated per-task diff. Send a follow-up to continue the same managed conversation.
5. In VS Code, use **Agent HUD: Assign Work** or the plus button in **Agent HUD Tasks**. Click a task to read its result and choose a next action. The Command Palette also exposes Follow-up, Answer Agent, Interrupt, Resume, and Reconnect.
6. **New Pair** retains the planner/builder/reviewer flow, plan approval, test command and bounded review rounds. Prefer a separate worktree. Direct-checkout pairs require a clean checkout; unexpected review edits are preserved and pause the pair. Full autonomous pair execution was not revalidated in this session.

Agent CLI authentication is reused. No new API key or terminal is required. The extension bundles the broker; machine-scoped `agenthud.brokerPath` can override it. If you override `AGENTHUD_HOME` for the desktop app, set `agenthud.home` to the same directory in VS Code.

## Architecture traced

- `agenthud-report` normalizes agent hooks into an append-only event log. `EventTailer`, `SessionStore`, process scanners and Claude/Codex transcript scanners feed the existing panel, history, notifications and watched-session status. Process presence confirms liveness; it does not prove an agent is working or awaiting permission.
- `CoordinatorModel` combines watched sessions with broker-owned sessions and incremental `ChatTranscript` reads. Managed state wins over hook guesses. The desktop coordinator has a project/session rail, conversation, pinned requests, composer and activity column.
- The native floating panel configures its window style before attaching SwiftUI and keeps it stable afterward. Collapse hides the native window, focus actions expand it, and visibility/mode changes refresh the hosting view. In Coordinator mode only pane headers move the window, leaving composer and scrollbar gestures available. Process scans reuse one table and resolve each terminal device once per snapshot; missing terminal names are not cached across scans.
- `BrokerClient` connects to an owner-only Unix socket. `agenthud-broker` owns the agent processes independently of the desktop app and editor, broadcasts coalesced snapshots, and atomically saves task state. App/editor reloads reconnect to those processes. A broker restart preserves the task/conversation/outbox and marks execution stopped; it does not silently rerun potentially completed work.
- `ClaudeDriver` uses a long-lived print-mode stream-JSON process with host tool approvals. Follow-ups are explicitly queued and forwarded one turn at a time. `CodexServer` owns an app-server over stdio; `CodexDriver` uses initialize, thread start/resume/fork, turn start/steer/interrupt and server approval/question requests. Startup messages queue until the thread exists. RPC failures/timeouts surface errors rather than leaving silent spinners.
- `PairEngine` retains the existing orchestration logic and `BrokerService` performs git/test actions. Pair startup's asynchronous thread race was fixed by queuing driver input during startup.
- `extensions/agenthud-vscode` is a dependency-free local UI extension. Each actual extension host reports its workspace folders, trust, remote authority, focus and a connection identity. Heartbeats run every 15 seconds; stale connections are expired by the broker. Folder updates and socket closure update discovery. Paths are canonicalized and matched by directory boundaries, with the closest workspace and focused window preferred. Reconnect retains identity; reloading registers a new host. Projects are deduplicated by canonical root.
- Editor IPC exposes only Show Tasks, Review Changes and Open Result. Requests route to a matching connected window and are acknowledged by that extension host. No arbitrary commands or keystrokes are accepted over this bridge. Socket peers must be the same user; frames and outbound buffering are bounded, and socket writes run off the broker's event queue.

## What worked and what changed

The existing hooks, transcript parsing, persistent broker and pair engine were useful foundations. The missing connection was between real workspaces and real execution: projects only appeared after agent activity; completion/failure/disconnection often looked idle; start/send failures could lose drafts or leave busy state; and editor handoff depended on clipboard/accessibility behavior.

The bridge now discovers projects before any agent runs and supports assigning work directly in the correct existing workspace. Managed task state, delivery acknowledgments, current activity, completed replies and recoverable errors appear in both surfaces. The broker rejects duplicate ownership of a managed conversation, retains uncertain delivery records on restart and bounds queued inputs. Desktop drafts persist through app restarts. Missing/stale prompts and absent editor bridges return useful failures. Newer brokers are not shut down by the updated desktop client merely because they use a newer protocol.

## Supported integration boundaries

VS Code's public [workspace/window API](https://code.visualstudio.com/api/references/vscode-api) reports the current extension host's folders and provides view/document/command APIs. It does not expose ownership of another extension's private agent transport. The [CLI's reuse-window option](https://code.visualstudio.com/docs/configure/command-line) targets the last active window; it is insufficient for choosing a specific project's window. The bridge therefore routes actions to its own connected host. The UI extension location follows [VS Code's remote-extension guidance](https://code.visualstudio.com/api/advanced-topics/remote-extensions); remote workspaces are reported but local execution is explicitly unavailable.

The installed Codex CLI generated its own JSON schema, confirming the thread, turn, approval and sandbox fields used here. Its app-server is a supported client integration mechanism, as described in [OpenAI's App Server documentation](https://learn.chatgpt.com/docs/app-server). The running Codex VS Code extension uses a private stdio app-server; this coordinator owns a separate app-server for its managed tasks.

A watched panel is not converted into a broker-owned session merely because its project is known. For existing Codex chats, `CodexIPC` connects to Codex's same-user local socket, discovers the exact thread's live owner, reads its settings, and uses a short-lived follower snapshot to decide whether to start a follow-up or steer the running turn. Requests are targeted to that owner and keep its settings. There is no resume, fork, ownership takeover or second agent process. Versioned responses and thread identity are checked; unsupported versions fail visibly. Probes run off the UI thread, every five seconds for only the selected chat, and do not fetch its history. Only an actual send reads a bounded live snapshot.

This is a compatibility adapter to Codex's internal owner/follower protocol, rather than a documented public extension API. The installed extension provides `thread-owner-discovery` v1, `thread-follower-read-model-settings` v1, `thread-stream-state-changed` v11, `thread-follower-start-turn` v2 and `thread-follower-steer-turn` v1. The documented [IDE commands](https://learn.chatgpt.com/docs/ide/commands) expose focus/context commands, not a send-to-thread command. The adapter checks compatibility and fails safely if Codex changes the protocol. Codex's queue-state replacement API is deliberately avoided because replacing it could lose replies typed in the editor.

The coordinator persists delivery receipts and keeps the draft until acknowledgment. Only a timestamped matching user message in the same transcript marks it Delivered. A disconnected or ambiguous mutation is marked uncertain and never replayed. After an app restart, an unfinished delivery is shown as uncertain until checked. The pre-existing Claude URL/accessibility adapter remains a best-effort handoff; unsupported hosts offer explicit Copy & Open or Continue a Copy Here.

## Repeat checks

```sh
swift test
node --test extensions/agenthud-vscode/client.test.js
python3 scripts/test-broker.py
make app vscode-package
python3 scripts/broker-smoke.py
```

The smoke script reads the real broker by default and can start read-only checks, send a follow-up, answer a pending test question, route editor result/review actions or stop a selected smoke session. Its isolated-process counterpart never calls a model.

For native visibility diagnostics, launch the local app executable with `AGENTHUD_PANEL_TRACE=1` and redirect stderr to a local file. Its panel traces contain visibility flags and geometry, never draft or conversation text. This is off by default.
